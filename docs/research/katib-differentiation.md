# Differentiating Kronik from Jason Cameron's Katib API

**Research date:** 2026-08-10  
**Katib baseline:** [`JasonLovesDoggo/Katib` at `c8e9968`](https://github.com/JasonLovesDoggo/Katib/tree/c8e996848f94d5af7a57254a7377adcc603d0971), plus live observations on 2026-08-10  
**Kronik baseline:** [`Matthieusz/kronik` at `1ca1b1c`](https://github.com/Matthieusz/kronik/tree/1ca1b1c8137b810840a8b2e5902527baed1ca838)

## Executive answer

Kronik should not differentiate by adding more vanity metrics to Katib's three-endpoint shape. Its credible position is **portfolio evidence with explicit semantics**: anonymous access by default, optional bring-your-own-token access for trusted server-side integrations, broad public default-branch commit discovery, exact attribution and Git graph data, bounded and disclosed coverage, reproducible windows, stable pagination, typed failures, and cache provenance.

That position is already visible in Kronik's domain language and v1 contract. Katib is a lightweight showcase API whose implementation samples a user's recently updated owned repositories and then presents commits, aggregate changes, repository languages, and streaks. Kronik can meaningfully diverge by making every number answer: **what was counted, why it belongs to this user, over which interval, how complete it is, and how fresh the evidence is**.

The highest-priority next step is therefore to productize Kronik's existing semantic advantages rather than expand scope immediately. After that, the strongest defensible direction is an opt-in, repository-backed portfolio manifest and explainable evidence bundles. Historical trends and broader contribution types are promising but require new storage and much harder semantics.

This report uses Katib's public source, README/history, issues, deployment declaration, live docs, and live GET responses; Kronik's `CONTEXT.md`, README, ADRs, implementation/release documents, docs, and generated contract; and GitHub's official API documentation. Source links are pinned to the inspected commits where possible.

## Verified Katib capabilities and boundaries

### Product and API

- **Verified — source:** Katib describes itself as a GitHub activity API for portfolios and dashboards. Its current README lists latest commit, recent commit history with statistics, contribution streak, language analysis, caching, and GitHub PAT support ([README](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/README.md)). Its initial README was more explicitly editorial: a “personal GitHub curator” intended to filter noise and showcase impressive contributions ([historical README](https://github.com/JasonLovesDoggo/Katib/blob/5b4aab04b383cbbbfe02f6a196312639b32f3dc1/README.md)).
- **Verified — source:** the registered routes are `GET /commits/latest`, `GET /v2/commits/latest`, `GET /streak`, `GET /healthcheck`, and the HTML docs at `/` ([`main.go`](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/main.go)). No OpenAPI document, cursor/page continuation route, or date-window input is present in the inspected tree. This is an implementation observation, not a claim about private plans.
- **Verified — live:** `/healthcheck` returned `200 {"status":"ok"}`; the three documented activity routes returned JSON for the whitelisted `jasonlovesdoggo` account; and a request for `octocat` without a PAT returned `401` ([health](https://katib.jasoncameron.dev/healthcheck), [latest](https://katib.jasoncameron.dev/commits/latest?username=jasonlovesdoggo), [list](https://katib.jasoncameron.dev/v2/commits/latest?username=jasonlovesdoggo&limit=2), [streak](https://katib.jasoncameron.dev/streak?username=jasonlovesdoggo)). The live landing page documents the same three activity routes ([live docs](https://katib.jasoncameron.dev/)).

### Commit and aggregate semantics

- **Verified — source:** Katib does not search GitHub globally for a user's commits. For latest commit it examines the first 10 public repositories owned by the requested user, ordered by update time, and the first five default-branch history entries in each. The list endpoint examines the first 20 such repositories and first 10 history entries per repository ([`getters/LatestCommit.go`](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/getters/LatestCommit.go)). Commits to repositories owned by organizations or other users are therefore outside this traversal.
- **Verified — source:** both paths filter by the GitHub-resolved commit author's login, case-insensitively. This was added after Katib issue #2 reported commits in owned/forked repositories that were not authored by the requested user ([issue #2](https://github.com/JasonLovesDoggo/Katib/issues/2), [fix PR #4](https://github.com/JasonLovesDoggo/Katib/pull/4)). Katib should not be described as lacking author filtering at the inspected revision.
- **Verified — source:** Katib returns abbreviated object IDs. Its `parentCommits` values are earlier sampled commits in the same repository, not the selected commit's actual Git parents ([`getters/LatestCommit.go`](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/getters/LatestCommit.go)).
- **Verified — source:** v2 sorts the sampled commits by committed date and applies `limit` only to the returned commit array. `stats` totals all sampled matches, not necessarily the returned items, and the implementation does not expose a completeness or coverage field. Invalid or non-positive limits silently become 10 ([route](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/routes/commits_v2.go), [getter](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/getters/LatestCommit.go)).
- **Verified — source:** language values aggregate repository language edges for sampled owned repositories containing a sampled matching commit. If the leading language exceeds 80%, Katib deliberately reduces it by 40% and redistributes those units to other languages ([`normalizeLanguages`](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/getters/LatestCommit.go)). The result is presentation-oriented, not exact provider evidence.
- **Verified — source:** three repositories are hard-coded out only for `jasonlovesdoggo`; no caller-controlled inclusion/exclusion mechanism exists in the inspected contract ([`getExcludedRepos`](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/getters/LatestCommit.go)).

### Streak, authentication, errors, and infrastructure

- **Verified — source:** Katib queries GitHub's contribution calendar and returns `currentStreak`, `highestStreak`, and `active`. It tolerates an empty today when yesterday was active, but neither the response nor live docs expose the evaluated `from`/`to` range ([`getters/StreakInfo.go`](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/getters/StreakInfo.go), [live docs](https://katib.jasoncameron.dev/)). A historical README called this an “all-time best,” but the inspected query itself does not establish an all-time range ([historical README](https://github.com/JasonLovesDoggo/Katib/blob/68d99f37e58c3b02146c6dc201c36329c3e9ef48/README.md)).
- **Verified — source/live:** only three hard-coded usernames use Katib's service credential. Every other username must send a caller-owned GitHub PAT in `Authorization` ([middleware](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/middleware/auth.go)); the live `octocat` request confirmed the `401` behavior. GitHub documents 60 unauthenticated REST requests per hour versus generally 5,000 for authenticated users, explaining the quota pressure but not requiring Katib's caller-PAT design ([GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28)).
- **Verified — source:** route failures are ad hoc JSON; getter failures become `500` with the underlying error string. There is no typed public error taxonomy in the inspected source ([commit route](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/routes/commits.go), [streak route](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/routes/streak.go)).
- **Verified — source:** activity responses use a process-local in-memory cache for 120 seconds ([`main.go`](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/main.go)). Katib's Fly declaration permits scale-to-zero and names Toronto as primary region ([`fly.toml`](https://github.com/JasonLovesDoggo/Katib/blob/c8e996848f94d5af7a57254a7377adcc603d0971/fly.toml)). It would be an assumption to infer actual machine count, traffic, latency, or uptime from this configuration.

## Overlap and meaningful divergence

| Area           | Katib, verified at baseline                                                                                   | Kronik contract/design at baseline                                                                                                      | Meaningful difference                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Latest commit  | Sampled from recently updated user-owned repositories; abbreviated SHA; prior sampled commits labeled parents | Public default-branch commit across any owner; full SHA; actual Git parent references; authored and committed times                     | Kronik is evidence-correct and includes external/open-source work                        |
| Commit feed    | One bounded sample with a display limit; no continuation                                                      | Bidirectional, authenticated opaque cursors, snapshot stability, one-hour expiry                                                        | A stable feed rather than a one-shot showcase sample                                     |
| Aggregates     | Totals over sampled matches with no time window or completeness signal                                        | Inclusive 30-day default / 90-day maximum window; at most 100 aggregated commits; matched/aggregated/complete coverage                  | Reproducible, bounded claims whose incompleteness is visible                             |
| Languages      | Repository languages for sampled repos; dominant values can be redistributed                                  | Exact GitHub bytes for unique repositories with matching commits; tail conserved in `otherBytes`; explicitly not authorship/proficiency | Truthful composition rather than aesthetic normalization                                 |
| Streak         | Current/highest/active without output range                                                                   | Current/longest plus exact trailing 365-date range; explicitly not all-time                                                             | The label states what the provider evidence can support                                  |
| Identity       | Username query input; no canonical user object in result                                                      | Path-scoped user resource; canonical login, URL, and avatar in result                                                                   | Stable resource semantics and case normalization                                         |
| Authentication | Caller PAT is mandatory for non-whitelisted users                                                             | Anonymous reads with a service-owned credential; optional caller credentials are proposed                                               | Keeps zero-secret embedding while letting server-side callers use their own GitHub quota |
| Errors/docs    | Manual HTML and ad hoc JSON errors                                                                            | Effect Schema contract, generated OpenAPI/Fumadocs, stable RFC 9457-style problems                                                      | Machine-consumable and evolvable integration contract                                    |

## Product philosophy and positioning

### Recommended thesis: “trustworthy public work evidence”

Katib's historic language—curation, “meaningful” work, showing prowess—and its dominant-language redistribution reveal a showcase-first philosophy. That is useful, but it makes editorial choices look like measurements. Kronik's stronger philosophy is:

1. **Evidence before inference.** Return provider-backed commits, graph references, dates, and bytes; do not convert them into productivity, impact, or proficiency claims.
2. **A boundary is part of every metric.** Windows, result caps, search incompleteness, and streak ranges must travel with values.
3. **Integration safety is product value.** Anonymous reads should remain the default. Optional caller PATs can supplement that path for trusted server-side integrations, provided Kronik never stores or logs them, never exposes private data, and never requires a token in browser-based embeds.
4. **Open-source work is first-class.** Repository ownership must not determine whether authored work appears.
5. **Freshness is observable.** Consumers should decide whether stale-but-valid evidence is acceptable rather than receiving an unexplained cache.

This is more defensible than “Katib, but with cleaner routes.” Route and field changes are easy to copy; a maintained semantic specification, conformance corpus, reliability architecture, and integrations built around provenance compound over time.

### Why the top priorities come first

- **P0 truth contract** turns work already present in `CONTEXT.md`, schemas, tests, and docs into a recognizable product promise. It is the cheapest way to stop being perceived as a Katib clone.
- **P0 embed safety** keeps ordinary browser-based portfolios zero-secret. Optional bring your own token should complement this anonymous path for trusted server-side callers rather than replace it. Per-user coordination still protects both service and caller quota ([coordination ADR](https://github.com/Matthieusz/kronik/blob/1ca1b1c8137b810840a8b2e5902527baed1ca838/docs/adr/0002-cloudflare-worker-with-per-user-coordination.md)).
- **P0 optional bring your own token** addresses exhaustion of Kronik's shared GitHub quota by charging cache-miss work to the caller's token. This reverses the credential policy in [ADR 0003](https://github.com/Matthieusz/kronik/blob/1ca1b1c8137b810840a8b2e5902527baed1ca838/docs/adr/0003-service-owned-github-credentials.md), so implementation should begin with a superseding ADR and threat model rather than an implicit exception.
- **P1 evidence bundles** deepen, rather than widen, the module: they let portfolio UIs explain a number and preserve its scope. The feature should expose provenance, not invent an unverifiable “trust score.”

## What not to pursue as differentiation

- **Katib wire compatibility.** Kronik has already accepted a coherent v1 over accidental compatibility ([ADR 0001](https://github.com/Matthieusz/kronik/blob/1ca1b1c8137b810840a8b2e5902527baed1ca838/docs/adr/0001-coherent-v1-over-wire-compatibility.md)). Compatibility would preserve Katib's ambiguous fields and auth shape while weakening Kronik's thesis.
- **“All-time” streaks without all-time evidence.** Keep the evaluated range in the response.
- **Language proficiency or personal-authorship percentages.** Repository language bytes describe repositories, not what one person wrote.
- **A hidden “meaningful commit” score.** Line thresholds, merge exclusion, message sentiment, and repository popularity are editorial policies. If users eventually curate, make the policy explicit and opt-in through a manifest.
- **Unlimited or silently partial totals.** GitHub search and quota boundaries are product facts, not implementation details.
- **Mandatory or browser-exposed caller PATs.** Optional server-side bring your own token is useful, but Kronik should not require it for ordinary reads or instruct portfolio authors to ship a token to visitors. Caller credentials must be ephemeral and redacted, and must never broaden the response beyond public GitHub data.
- **Infrastructure as the headline.** Effect, Cloudflare, Durable Objects, and schema-validated RPC enable the promise; users buy trustworthy, fast, safe evidence rather than a stack diagram. The separate RPC boundary remains valuable engineering policy ([ADR 0006](https://github.com/Matthieusz/kronik/blob/1ca1b1c8137b810840a8b2e5902527baed1ca838/docs/adr/0006-schema-validate-durable-object-rpc.md)).

## Assumptions and unknowns

- Katib publishes no usage analytics, SLOs, roadmap, or production topology. This report does not infer its adoption, cost, latency, or future plans.
- Live observations are a dated snapshot. They verify responses seen on 2026-08-10, not a contractual guarantee.
- Absence of OpenAPI, pagination, date windows, or caller customization means only that those facilities were not found in the inspected public revision and live docs.
- Katib's source traversal can omit qualifying work, but this report does not estimate how often real users are affected.
- Kronik's contract and local verification are strong implementation evidence, but its own release report leaves production edge behavior and live GitHub behavior unverified.
- Optional caller PATs are not yet part of Kronik's accepted architecture. Their safety depends on proving that an overprivileged token cannot cause private repositories or contributions to enter public responses, logs, caches, cursors, or observability.
- Katib has no license file or detected GitHub license at the inspected revision. Kronik correctly records independent reimplementation rather than source reuse ([ADR 0005](https://github.com/Matthieusz/kronik/blob/1ca1b1c8137b810840a8b2e5902527baed1ca838/docs/adr/0005-independent-katib-feature-parity.md)).

## Recommended sequence

1. **Position v1 publicly around evidence semantics**, with one side-by-side example showing external-repository coverage, actual parents, exact language bytes, bounded streaks, and partial coverage.
2. **Verify the production delivery promise** before marketing edge/global availability: deploy only with separate approval, run the live smoke and cache/coalescing checks, and publish observed SLOs only after measurement.
3. **Record the new credential decision in a superseding ADR, then design optional server-side bring your own token.** Keep anonymous access as the default; use caller credentials only for upstream work; enforce public-only results even for overprivileged tokens; never persist, log, or place raw tokens in cache keys or cursors; and distinguish invalid credentials from exhausted GitHub quota. This reduces pressure on Kronik's shared quota but does not eliminate GitHub rate limiting.
4. **Design explainable evidence metadata** as a narrow contract addition; avoid scores or generated prose.
5. **Prototype a repository-backed manifest** with one use case—repository inclusion/exclusion—before adding pins, labels, or rendering preferences.
6. **Defer historical storage and broader contribution types** until usage shows whether users value evidence, customization, or trend narratives most.

The strategic test for every future feature should be: **does it make public work easier to embed and harder to misrepresent?** If not, it is probably feature parity or vanity-stat expansion rather than meaningful differentiation.
